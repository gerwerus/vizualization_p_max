Динамические воркеры без двухфазного релиза

LAVKAPROJECTS-6946 · как partition_key и константа P_MAX разводят «куда лежит событие» и «кто его обрабатывает»

1. Две разные вещи

partition_key — свойство строки в events. Считается один раз при INSERT и никогда не меняется.

N (workers) — настройка перекладчика в рантайм-конфиге. Меняется без выкатки.

partition_key = md5(поле_сущности) % P_MAX   // P_MAX = 16, константа кода
воркер i владеет ключами { k ∈ [0, P_MAX) : k % N == i }

P_MAX задаёт фиксированное число «корзин» (0…15). События одной сущности всегда попадают в одну корзину — независимо от N.

2. Интерактив: меняем N — события не переезжают

Три сущности (заказы) с фиксированными ключами. Подвинь слайдер — меняется только цвет воркера, не позиция сущности.

P_MAX = 16 (фиксировано в коде)
Заказ α key = 3 →
Заказ β key = 7 →
Заказ γ key = 11 →

Все 16 ключей (корзин P_MAX):

При N=2 → N=4 заказ β остаётся в корзине 7. Меняется только владелец: воркер 1 → воркер 3. События β не оказываются в двух корзинах одновременно → порядок не рвётся.

3. Почему не нужен двухфазный релиз: лок на ключ

Каждый ключ обрабатывается под блокировкой event_push-{db}-{shard}-{type}-p{k}. Новый владелец не может начать, пока старый не отпустит лок.

4. Отклонённая альтернатива: hash(pk) % N

✓ md5(pk) % P_MAX (наш дизайн)

Ключ в строке, N только делит владение.

  • События сущности всегда в одной корзине
  • Смена N = смена владельца, не переезд данных
  • Лок на ключ → безопасный handoff
  • Писателям N знать не надо

✗ hash(pk) % N (отклонено)

Ключ зависит от текущего N.

  • При N=2: заказ → корзина 1
  • При N=4: тот же заказ → корзина 3
  • Старые и новые события в разных корзинах
  • Два воркера обрабатывают параллельно → порядок сломан

5. Зачем именно P_MAX, а не «просто N воркеров»

P_MAX — стабильная гранулярность в данных. N — операционный рычаг.

P_MAX = 16 N workers
Где живёт колонка в events динамический конфиг
Меняется только выкаткой (+ окно partitioned:false) из админки, раз в 60 с
Знают писатели да (всегда % 16) нет
Потолок параллелизма 16 независимых локов на (shard, type) сколько реально поднято (≤ P_MAX)

Без P_MAX пришлось бы либо привязать ключ к N (двухфазный релиз), либо при N=1 обходить все ключи впустую — P_MAX фиксирует «решётку», а N лишь группирует ячейки между воркерами.
